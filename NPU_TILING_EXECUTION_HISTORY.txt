Ascend MatMul tiling execution issue record
Updated: 2026-07-27

Purpose
-------

This file records why the earlier NPU runs did not validate the tiling search,
and the boundary used by the current implementation. It is not a list of
candidate performance results.

Sections 14 through 18 describe earlier BASE-only or callback-family-limited
strategies. They are retained as history, but section 20 supersedes their
search boundary.

What the earlier failures meant
===============================

1. aclInit rc=507008

The old AscendC host-stub runner could load a different HAL/runtime dependency
set from the minimal ACL program. That was a runner linkage problem before any
MatMul tiling or kernel was executed.

2. RegisterAscendBinary ret=107000 followed by C index=0 coverage failure

The generated host stub failed to register its embedded custom kernel. The stub
then returned without executing that kernel, so the poisoned output remained
unchanged. The coverage message was therefore secondary and was not evidence
that the candidate tiling was invalid.

3. aclrtSynchronizeStream rc=507015

The custom kernel consumed TCubeTiling through a different scheduling/template
contract from the official MatMulV3 implementation. MultiCoreMatmulTiling
acceptance does not make an arbitrary custom wrapper compatible with every
MatMulV3 ND2NZ, tail, transpose, split-K, and output path.

4. Generic SoC used by the search

The detector found Ascend910B3 but wrote:

  SOC_VERSION=Ascend910B

The search therefore queried a generic PlatformAscendC model while the NPU
operator used the exact B3 compile information. This could generate candidates
with an AIC count and memory model that did not match the official MatMulV3
runtime-bank filename and operator context.

5. Build phase reported only "NPU run failed"

Compiler and linker output was redirected to build/host_build.log or
build/kernel_build.log, while the outer error handler inspected only the phase
log. The build wrapper now emits the failing step, return code, nested log path,
and the last compiler/linker diagnostics directly to the terminal.

6. CANN 8.1 linker could not find -loptiling

On the tested CANN 8.1 installation, liboptiling.so is stored under:

  opp/built-in/op_impl/ai_core/tbe/op_tiling/lib/linux/aarch64

It is not necessarily exposed through the platform lib64 linker search path.
The project CMake now resolves that existing file explicitly and links its
absolute path. No toolkit symlink or global library path is changed.

7. Use the documented RuntimeKb API sequence

The first bank probe called version-specific RuntimeKb::QueryBank overloads.
The CANN 8.1 public sequence used now is:

  RuntimeKb::InitBank(fe::PlatFormInfos *)
  RuntimeKb::QueryBank(src, size, opType, tiling)

Every generated record must return rc=0 and a non-null tiling object.

8. CANN 8.1 platform and RuntimeKb ABI details

The platform header is under the experimental include tree:

  include/experiment/platform/platform/platform_info.h

The CMake target adds that include path only to the bank-probe target. RuntimeKb::InitBank
returns bool: true means success. Treating its value as an integer return code
incorrectly reported successful initialization as rc=1.

9. MatMulV3 L2 fields must exactly cover the scheduling grid

The old bank writer set l2MTileCnt and l2NTileCnt to zero. The MatMulV3 base
kernel uses these values as L2 loop bounds and the host source explicitly
requires them to be legal. A zero count can leave the output poison unchanged,
which produced:

  official output coverage failed at C index=0

Positive values alone are insufficient. The kernel computes its output-block
grid from:

  mTotal = ceil(M / singleCoreM)
  nTotal = ceil(N / singleCoreN)

The L2 count/block fields must cover that grid exactly, including a positive
tail no larger than one full L2 block. The bank writer now derives all four L2
fields from this singleCore grid and validates both tails before writing a
record.

10. Generic MultiCoreMatmulTiling output is not automatically a BASE bank record

The failed record for llm_full_4096_ffn_up used:

  shape       4096 x 11008 x 4096
  singleCore  208 x 11008 x 4096
  base        208 x 144 x 64
  failure     C[0, 11007] remained 0x5a5a

RuntimeKb accepted the schema and hash, but the official MatMulV3 host source
does not run its normal semantic tiling checks after a bank hit. It copies all
23 knowledge fields directly. The source-generated tilingEnable=BASE path sets
singleCoreM=baseM and singleCoreN=baseN. Larger singleCore M/N values are
produced only together with specialized full-load or split-K template keys.

The search now treats this as a template contract:

  tilingEnable=BASE:
      singleCoreM == baseM
      singleCoreN == baseN

Beam, Tabu, and LNS still search baseM/baseN/baseK, traversal, and buffering.
They do not inject a generic MultiCoreMatmulTiling M/N partition into the wrong
MatMulV3 template.

11. MULTI_CORE_SPLIT_K is exactly one tile per launched core

The official kernel maps blockIdx directly to one (m, n, k) tile and has no
multi-round loop or idle-core guard. Therefore:

  ceil(M/singleCoreM) * ceil(N/singleCoreN) * ceil(K/singleCoreK)
      == usedCoreNum

This equality is enforced while generating candidates, before Beam pruning.
Allowing fewer logical tiles than launched cores can make extra cores address a
K tile beyond the logical range.

12. BASE and MULTI_CORE_SPLIT_K have different idle-core rules

MatmulBaseBlock computes realRound=0 for BASE cores that receive no output
block. Therefore BASE may safely use more cores than its M/N block count. The
earlier static rule usedCoreNum <= M-blocks*N-blocks incorrectly rejected small
M or N cases.

MULTI_CORE_SPLIT_K has no equivalent idle-core check after blockIdx is mapped
to kIndex, so the exact equality in item 11 remains mandatory.

Current execution boundary
==========================

The project no longer compiles or launches a custom MatMul kernel.

  exact detected SoC
      -> constraint-aware Beam + Tabu/LNS
      -> MultiCoreMatmulTiling::GetTiling/GetCoreNum
      -> static capacity/template validation
      -> project-local MatMulV3 TUNE_BANK_PATH record
      -> RuntimeKb::InitBank + QueryBank acceptance
      -> installed aclnnMatmul / official MatMulV3 kernel
      -> numerical or coverage preflight
      -> ACL Event timing

The baseline uses the same installed aclnnMatmul path with an empty project-local
tuning-bank directory, so only the injected tiling differs.

Runtime-bank checks performed before NPU timing
===============================================

- Exact SoC and AIC count must match the installed MatMulV3 bank filename.
- The installed bank input-key and knowledge schemas must match.
- The packed MatMulV3 input key must be exactly 183 bytes.
- CANN RuntimeKb::CommonHash must reproduce the ID of an installed bank record.
- RuntimeKb::InitBank uses the exact SoC platform information.
- RuntimeKb::QueryBank must return rc=0 and a non-null tiling object.
- L2 tile counts/blocks must be positive and exactly cover the singleCore M/N
  scheduling grid.
- A tilingEnable=BASE record must use singleCoreM/N equal to baseM/N.
- usedCoreNum must not exceed the exact platform AIC count.
- MultiCoreMatmulTiling return, GetCoreNum, Cube alignment, L0/L1/DB, M/N rounds,
  and split-K template constraints must all pass.

Unaligned M/N/K are not rejected merely for being tails. The official MatMulV3
operator owns its ND2NZ/NZ2ND and tail execution templates.

Split-K
-------

baseK < K is ordinary per-core K blocking.

singleCoreK < K is cross-core split-K. The current search emits the official
MULTI_CORE_SPLIT_K tuning mode only for FP32, transA=false, transB=true, and a
single scheduling round. Other cross-core reduction templates are not claimed.

Project isolation
=================

TUNE_BANK_PATH, ASCEND_CACHE_PATH, CANN paths, and SoC variables are set only
for run_npu.sh and its child processes. The project does not modify toolkit
symlinks, shell profiles, drivers, firmware, or global system settings.

13. Long full run hid a candidate timeout behind a closed subprocess pipe

After 350 successful candidates, a full run stopped with:

  fatal: I/O operation on closed file.

The next candidate had not printed a start line because progress was emitted
only every ten candidates. The profiler used Popen stdout=PIPE followed by
communicate(timeout). If the timeout path observes a child that has already
closed stdout, the cleanup communicate call can operate on the closed pipe and
replace the real candidate timeout with this ValueError.

Candidate output now goes to a per-runner regular file. The parent uses wait()
for the timeout, terminates the isolated process group if needed, closes the
file, and only then reads it. A timeout can therefore report the exact
workload, rank, T/S/C/G/L2 schedule, and final runner lines.

14. BASE candidates bypassed the intended core-round budget

The BASE candidate keeps singleCoreM/N unset until MultiCoreMatmulTiling is
called, then the MatMulV3 BASE contract materializes:

  singleCoreM = baseM
  singleCoreN = baseN

The old HardLegal round check only ran when singleCoreM/N were already set.
Large shapes therefore entered NPU profiling with hundreds or thousands of
BASE output blocks, even though SearchOptions.maxCoreRounds was four.

The measured consequence was systematic:

  llm_8192_square       best searched / official speed = 0.896078
  vision_projection    best searched / official speed = 0.787998
  llm_full_ffn_down    best searched / official speed = 0.939847
  skinny_n_large_k     best searched / official speed = 1.49404

All clearly improved transcribed candidates used one or two core rounds. The
round guard now applies to the concrete BASE grid after baseM/N are present,
and the default budget is two rounds. Shapes outside that search envelope keep
the installed official operator.

15. Noise-aware selection and continuation workload

Profiling a candidate does not make it the deployed choice. The result summary
now selects searched only when its latency improvement exceeds the combined
measurement-noise threshold. within_noise and regressed results select the
official operator.

The 2026-07-27 run completed all Top-20 candidates for workloads 1 through 17
and ranks 1 through 10 for skinny_n_large_k. Its rank 1 already produced the
clear 1.49404x result. The default full continuation therefore uses
config/workloads_unmeasured.csv and does not repeat those workloads.

16. Two-round BASE search validation

The corrected host search was rebuilt for Ascend910B3 and checked without NPU
profiling or CPU simulation:

  platform AIC cores                         20
  remaining workloads                       10
  workloads with distinct searched BASE     2
  searched candidates sent to NPU            40
  official-fallback-only workloads           8

The retained workloads are large_k_small_mn and odd_tail_1, with 20 candidates
each. Every retained BASE record has traverse=0 and no more than 40 output
blocks. The known skinny_n_large_k winner remains proxy rank 1 at
baseMNK=208x32x64.

BASE traverse values were previously emitted three times even though
singleCoreM/N=baseM/N leaves only one M and one N tile inside each Matmul call.
Normal BASE candidates now use only the canonical traverse value. Direct
split-K keeps its template-specific traverse search.

The local validate-only test passed the CANN 8.1 RuntimeKb lookup for all
retained BASE and FP32 NT split-K records. It also asserts that high-round
large, tail, and BF16 BASE grids fall back to the installed official operator.
Improving those large shapes requires adding and validating the official
full-load template families; changing the BASE proxy alone cannot reproduce
their single-core reuse contract.

17. Remaining BASE run and missing MatMulV3 template families

The 2026-07-27 continuation run completed the remaining two workloads that had
legal two-round BASE candidates:

  large_k_small_mn  128x128x32768 fp16
    official          0.0327812 ms
    best BASE          0.0924664 ms
    official/BASE      0.354520
    decision           official

  odd_tail_1         257x1009x4097 fp16
    official          0.0495860 ms
    best BASE          0.0495156 ms
    official/BASE      1.001420
    decision           official (within noise)

The other seven supported continuation workloads had no legal searched BASE
candidate under the two-round limit. They were official-baseline-only results,
not measured search regressions. INT8 belongs to a different operator path.

The clear large-K regression has a structural cause. The current search emits
MatMulV3 tilingEnable=0 (BASE), except for the narrowly supported FP32 NT direct
atomic mode. The installed CANN 8.1 MatMulV3 implementation also dispatches:

  tilingEnable=2   single-core Split-K
  tilingEnable=3   deterministic multi-core Split-K
  tilingEnable=10  AL1 full load
  tilingEnable=20  BL1 full load

The installed liboptiling implementation and the matching public host source
use K >= 27392 as a Split-K trigger. For M=N=128, K=32768 on 20 AICs, the
128-based M/N output grid has one tile, which is below half the available
cores, and K is large enough for multi-core K partitioning. This shape is in
the official deterministic Split-K selection domain. Injecting a BASE record
there removes the template that makes the official path fast; reranking more
BASE tiles cannot recover it.

Future search must be hierarchical:

  template family
    -> legal single-core M/N/K partition
    -> baseM/baseN/baseK and L1/DB choices
    -> official RuntimeKb acceptance
    -> isolated NPU preflight
    -> timing and noise-aware official fallback

No further broad BASE profiling should be requested before tilingEnable=2/3
generation, workspace accounting, and template-specific static validation are
implemented. The previously measured skinny_n_large_k 1.49404x result remains
the only clear searched improvement so far.

18. Full callback contract and current search boundary

The RuntimeKb MatMulV3 record contains 23 tuning fields, but those fields are
not the complete tiling blob. After a bank hit, the official callback derives
additional ND-to-NZ and cache fields. In the CANN 8.1 callback used here, the
full blob is 272 bytes and includes, after TCubeTiling and L2 scheduling:

  l2CacheFlag
  baseAN
  baseAD
  baseBN
  baseBD

Replaying the official 23 fields through RuntimeKb can therefore differ from
the empty-bank official path even when baseM/baseN/baseK are identical.
skinny_n_large_k is a concrete example: the visible 23 fields are the same,
but baseBD differs. The profiler now measures three distinct paths:

  official baseline      empty project tuning bank
  bank_seed_control      official 23 fields replayed through RuntimeKb
  searched               searched 23 fields replayed through RuntimeKb

The control is not an optimization result. A searched candidate must beat the
official baseline and the bank-path control beyond noise before the program
reports a proven tiling improvement.

Two static checks were also corrected:

  - stepKa and stepKb themselves must be integral K-step multiples. Requiring
    the total K iteration count to divide them rejected official legal tails.
  - Ascend910B3 reports 524032 usable L1 bytes while the official tiler may use
    the 512-byte-aligned 524288-byte capacity. Static validation now follows
    the official alignment boundary instead of rejecting the official seed.

The current CANN 8.1 callback selects BASE for 26 supported corpus workloads
and DETERMINISTIC_SPLIT_K for large_k_small_mn. Candidate generation is
conditioned on that observed template contract. It no longer approximates a
Split-K or full-load kernel by injecting a BASE record with unrelated
singleCore values.

The analytical ranker now models, per critical core:

  Cube block work and pipeline fill/drain
  GM/L2-to-L1 bytes and transaction starts
  L1-to-L0 depth and step reuse
  L0A/L0B/L0C buffering overlap
  FixPipe 512-byte row packets
  ND-to-NZ derived work
  L2 working set, tails, and 20-AIC scheduling rounds

Beam Search keeps separate beams per kernel template. Tabu/LNS mutates only
legal discrete neighbours. Every selected record is then round-tripped through
the official MatMulV3 callback and RuntimeKb before NPU execution.

Historical NPU data are reused only for an exact visible schedule fingerprint
on the same SoC, AIC count, shape, dtype, transpose state, template, base and
single-core shapes, core count, output grid, and L2 schedule. One historical
sample is assigned to at most one current candidate. Controls are never
fabricated from old data.

19. Resource overload and prevention

This host has about 1.9 GiB RAM and no swap. Two development operations caused
avoidable overload:

  - a broad source-repository search fetched many partial-clone blobs;
  - the first analytical model materialized every output tile of large shapes.

The model now computes full/tail axis sums and critical-core load in closed
form, so its memory is O(1) in the matrix dimensions. Repository research is
restricted to named files fetched individually. Build and validation run with
BUILD_JOBS=1; no CPU simulation, NPU profiling, or parallel compiler is started
on this host.

20. Full CANN 8.1 template implementation

The installed DAV C220 mat_mul_v3.cpp dispatches 12 suffixes in seven families:

  0/1          BASE
  20/21        SINGLE_CORE_SPLIT_K
  30/31        DETERMINISTIC_SPLIT_K
  101          AL1_FULL_LOAD
  200/201      BL1_FULL_LOAD
  10200/10201  BL1_FULL_LOAD_FIXPIPE
  20201        BL1_FULL_LOAD_VEC_NZ2ND

The current search constructs and ranks all seven families. It does not contain
the earlier invented FP32 NT split mode 4 because CANN 8.1 has no matching
kernel dispatch.

The BASE contract was corrected again after reading the exact installed kernel:
singleCoreM/N are output partitions and may be larger than baseM/N. The kernel
uses baseM/N/K inside each single-core partition. Requiring singleCoreM/N to
equal baseM/N caused the earlier 4096/8192 regressions by creating excessive
output tiles and fragmented L2 schedules.

usedCoreNum may also exceed the output tile count; unused AICs exit. This is
legal and is now penalized by the active-core cost model rather than rejected.

Host validation on CANN 8.1.RC1 and Ascend910B3 completed without NPU or CPU
simulation:

  general RuntimeKb records       45/45 found
  full-template RuntimeKb records 96/96 found
  searched full-template records  85
  kernel suffix coverage          12/12
  template family coverage        7/7

Every searched record selected for NPU preserved its requested family and all
23 knowledge fields through the official MatMulV3 callback. The full workload
corpus now includes shapes for every suffix. NPU latency is still required to
claim a performance improvement; host contract validation alone is not a
speedup result.

21. BASE output-coverage failure and corrected execution contract

The 20260727 full NPU run rejected this generated BASE record:

  workload  llm_full_4096_ffn_up
  shape     M=4096 N=11008 K=4096 fp16
  base      176x176x64
  single    832x352x4096
  L2        count=1x4 block=5x8
  failure   C row=2048 col=0 remained 0x5a poison

RuntimeKb returned found=1 because QueryBank verifies the hash/schema lookup and
deserializes the 23 knowledge fields. TranslateAoeTiling copies those fields and
checks tilingEnable; neither operation proves output coverage.

The generator had incorrectly treated ordinary BASE singleCoreM/N as arbitrary
multi-base output partitions. CANN 8.1 CalL1Tiling and CalL1TilingV200 set
singleCoreM/N to baseM/N. The installed ordinary BASE RuntimeKb records follow
the same contract; their only smaller values are logical tails within one
alignment unit. Larger single-core shapes belong to separate Split-K or
full-load templates with their own constraints.

The corrected ordinary BASE hard contract is:

  singleCoreK == K
  singleCoreM <= baseM <= align16(singleCoreM)
  singleCoreN <= baseN <= align16(singleCoreN)

The previous runner sampled only five C elements. That was insufficient to
certify an output schedule. Preflight now checks a 9x9 evenly spaced C grid
without copying the full output to host. A rejected searched candidate is
recorded as success=0 and discarded; because every candidate runs in its own
process, the next candidate can continue safely. A failed baseline or bank
control still aborts the run.

Old OCR candidate rows do not contain all 23 tuning fields and were measured
under the old five-point preflight. They remain as evidence but are not reused
as exact candidates. Official baseline history remains reusable.

22. Broad BASE search falsified; skinny-N optimization isolated

The 20260727 20-core NPU measurements falsified the broad BASE candidate
strategy. Across the first 18 completed workloads, the geometric mean of each
workload's best searched candidate was 0.99458 times the official operator
(about 0.54% slower). Excluding the one skinny-N winner, the geometric mean was
0.96982 (about 3.0% slower). Important regressions included:

  llm_full_4096_ffn_up  best speedup 0.767003
  llm_8192_square       best speedup 0.989526; many candidates 0.44-0.57
  attention_score_1024 best speedup 0.963880
  skinny_m_large_k      best speedup 0.813481

The cause was not insufficient Beam width. Generic MultiCoreMatmulTiling
results such as 176x176 were used as anchors for ordinary MatMulV3 BASE.
MatMulV3 uses the generic result only during initialization, then applies its
own SetBaseBlockTiling, CalL1Tiling, load-balance, and L2 rules. The generic
anchors are legal proposals but are not interchangeable with the final
MatMulV3 BASE policy. The analytical model therefore ranked legal but
architecturally poor large-matrix schedules.

The only repeatable large gain was:

  workload              skinny_n_large_k
  shape                 4096x17x16384 fp16 NN
  official              0.103036 ms
  bank control          0.104695 ms
  searched              0.0674828 ms
  speedup vs official   1.52685
  speedup vs bank       1.55144
  base/single           208x32x64 / 208x32x16384
  cores/grid            20 / 20x1
  L1 depth/step         16x8 / 8x4
  DB                    2x2x2
  L2                    5x1(4x1), order=1

For this shape, align16(ceil(4096/20)) is 208. It reduces the M output blocks
from 32 to exactly 20 and the four-core L2 waves from 8 to 5. The ratio 20/32
is 0.625, close to the measured latency ratio 0.0674828/0.103036 = 0.655.
The candidate also satisfies the reported 910B3 capacities:

  L0A = 208*64*2*2 = 53248 <= 65536
  L0B =  32*64*2*2 =  8192 <= 65536
  L0C = 208*32*4*2 = 53248 <= 131072

The default full run is now restricted to four ablations of this hypothesis:
core balance only, A-heavy L1 allocation, L0C double buffering, and L2 order.
The previously measured bank control and exact candidates are keyed by
template, T, S, cores, grid, L2, iterate order, L1, DB, and L2 order, so they
are reused rather than measured again.

The unrelated "I/O operation on closed file" was a host parser bug: an empty
runner CSV caused DictReader.fieldnames to be evaluated after the file context
closed. Header validation now occurs inside the context, and runner parse
failures retain the return code and runner tail. It was not evidence for or
against a tiling.

23. Historical candidate run-directory failure

The 20260728 focused run stopped before launching any candidate with:

  No such file or directory:
  .../candidate/skinny_n_large_k_bank_seed_control_rank0/run

An exact history match intentionally skips RuntimeKb candidate-directory
creation. The profiling loop nevertheless tried to create the nested run
directory before checking whether the control or searched candidate would be
reused from history. Since mkdir did not create missing parents, the run
failed before NPU execution.

Run directories are now created only for candidates that require a new NPU
measurement, with parent creation enabled. Historical controls and searched
candidates require no temporary run directory. The regression test covers
both paths. The focused RuntimeKb validation remains unchanged:

  bank_records_prepared=2
  history_records_reused=3

No measurement from the failed run needs to be preserved because it stopped
before the bank control or either new candidate was launched.

26. Exact persistent resume without repeated NPU measurements

The broad campaign previously regenerated temporary profile CSV files and
deleted them at exit. A later run could therefore measure the same successful
candidate again even when the complete tiling had not changed.

The profiler now maintains:

  results/npu_<mode>_resume.csv

It atomically merges each completed official baseline, bank seed control, and
searched candidate before temporary files are removed. The EXIT trap also
merges rows after a candidate failure or user interruption. Existing
npu_<mode>_candidates.csv is imported when upgrading from an earlier package.

Official baselines are reused only for the same SoC, AIC count, workload,
shape, dtype, and transpose flags. A bank control or searched candidate
additionally requires an exact match of:

  MatMulV3 template
  all 23 RuntimeKb knowledge words
  official callback tiling SHA-256

The visible baseMNK or singleCoreMNK fields alone are deliberately
insufficient. Old OCR rows without the hidden L1/DB/order fields remain
research evidence and are not presented as an exact resume match.

The terminal profile_plan reports exact assignments and the remaining NPU
work:

  resume_exact_baselines_assigned
  resume_exact_assigned
  npu_official_baselines_pending
  npu_controls_pending
  npu_searched_pending

No tiling candidate-generation rule was changed by this resume work.
